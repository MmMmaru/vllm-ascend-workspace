# 简洁代码解释

## 适用场景

当用户要求解释代码、追踪代码流，或询问某个行为/错误为什么发生时，启用本 skill。先读与问题直接相关的源码和调用方；不要只解释配置项或凭函数名猜测行为。

## 输出硬约束

### 解释正文

- 中文输出，正文严格控制为 2-3 个短段；简单问题用 2 段，跨文件或有异常分支时用 3 段。
- 每段 1-3 句，删除背景铺垫、重复结论和与问题无关的实现细节。
- 必须使用并覆盖以下五个标签；可以把多个标签放在同一段：
  - **目的（Why）**：为什么需要该功能，解决什么问题。
  - **输入（Input）**：用户/系统提供的数据，或触发执行的条件。
  - **处理（Logic）**：核心规则、计算、判断和调用顺序。
  - **输出（Output）**：产生的返回值、状态、张量、日志或异常。
  - **流向（Flow）**：数据从哪里来，经过哪些文件/函数，到哪里去以及由谁消费。
- “为什么会发生”类问题必须先给直接原因，再说明触发条件和影响；若存在多个可能原因，按证据强弱排序，不要把猜测写成结论。

### 数据流架构图

正文后必须给出一张紧凑的 ASCII 数据流图。禁止使用 Mermaid、PlantUML 或其他图形 DSL；节点标出角色，边标出传递的数据/状态/条件，至少包含输入、核心处理和输出消费者。

```text
[输入/触发条件]
        |
        v
[入口文件:函数]
        | 调用参数/数据
        v
[核心处理文件:函数]
        | 结果/异常
        v
[输出:直接消费者]
```

图后必须给出“代码定位”，按执行顺序列出涉及代码的详细路径和实际行号：

```text
代码定位：
1. `相对工作区路径:起始行-结束行` — `函数/类`：接收或产生什么数据。
2. `相对工作区路径:起始行-结束行` — `函数/类`：执行什么关键处理。
3. `相对工作区路径:起始行-结束行` — `函数/类`：输出由谁消费。
```

行号规则：

- 先用 `rg -n` 找符号，再用 `nl -ba <file>` 核对行号；不能凭记忆或猜测填写。
- 路径至少精确到工作区相对路径、文件名、函数/类和行范围；涉及多个仓库时注明仓库目录，例如 `vllm-ascend/...` 或 `vllm/...`。
- 行号应覆盖实际相关语句，而不是只标注整个文件；若源码未运行或行号可能因未提交改动变化，明确说明这是当前工作区的静态定位。
- 只保留直接支撑结论的 2-6 个定位点，避免把无关调用全部列出。

## 分析流程

1. **确定入口**：从用户提到的 API、类、函数、日志关键词或配置项开始，用 `rg` 找定义和调用点。
2. **按源码顺序追踪**：沿着“触发条件 → 输入构造 → 核心判断/计算 → 返回或副作用 → 消费者”读取代码；跨进程、跨模块或跨 rank 时标明边界。
3. **提取证据**：记录关键变量在每个节点的形状、类型、值域、设备、rank/进程归属或异常条件，只保留解释所需的信息。
4. **解释原因**：把错误信息与实际分支、类型/形状约束、调用顺序或资源状态对应起来。静态分析、单元测试、真实服务/E2E 结果必须区分表述。
5. **压缩输出**：先写 2-3 段正文，再画图，最后列带行号的代码定位；不要为了完整而展开无关背景。

## 证据与措辞

- 已运行验证才写“实测/验证通过”；只读源码时写“从源码看/静态分析表明”。
- 没有足够证据时，明确写“可能原因”并说明还缺什么日志、环境或复现条件。
- 对分布式或异步流程，标明发送方、接收方、同步点和最终消费者，不能用单进程线性描述掩盖数据边界。
- 对错误问题，输出顺序固定为：直接原因 → 触发链路 → 受影响的输出/行为 → 最小验证方式（如用户需要排查）。

## 最终格式

使用以下顺序，不增加额外的长篇章节：

1. 2-3 段“解释正文”，覆盖五个标签。
2. `数据流架构图`。
3. `代码定位`，列出 2-6 个路径和行号。
4. 仅在必要时补充一行“验证范围/未验证项”。
