# 代码解释（总分总）

## 适用场景

当用户要求解释代码、追踪代码流、理解模块设计，或询问某个行为/错误为什么发生时，启用本 skill。先读与问题直接相关的源码和调用方；不要只解释配置项或凭函数名猜测行为。

## 输出结构（总—分—总）

正文不限段落数，以把设计讲清楚为准，但每段都要有信息量，删除背景铺垫和重复结论。固定使用以下三段式结构：

### 第一部分（总）：整体数据流

- 用 1-2 段总述：这个功能解决什么问题（**目的/Why**），数据从哪里进入（**输入/Input**），经过哪些模块，最终产出什么并被谁消费（**输出/Output + 流向/Flow**）。
- 这一部分只讲主干，不展开模块内部细节；让读者先建立全局图景。
- 紧接着给出 ASCII 数据流架构图（见下节），作为“总”的可视化。

### 第二部分（分）：各模块设计

- 按数据流经过的顺序，逐个模块（文件/类/函数）讲解其设计，每个模块一个小节或小段。
- 每个模块必须讲清四点：
  - **职责**：该模块在整条链路中负责什么，为什么需要它存在（而不是合并进上下游）。
  - **输入**：接收什么数据/参数/状态，来源是谁；关键变量写明形状、类型、设备或 rank 归属（如与理解相关）。
  - **关键逻辑**：核心规则、分支判断、计算或调用顺序；只讲决定行为的逻辑，不逐行复述代码。
  - **输出与交接**：产出什么，交给下游哪个模块消费。
- 模块之间如有易混淆的边界（如编译期 vs 运行时、发送方 vs 接收方、patch vs 原生实现），明确指出。

### 第三部分（总）：总结

- 用 1 段把各模块串回整体：数据如何依次流过这些模块完成最终目标。
- 指出设计上的关键点或约束（例如为什么必须按这个顺序、哪个不变量不能破坏）。
- “为什么会发生/为什么报错”类问题，在总结处固定输出：直接原因 → 触发链路 → 受影响的输出/行为 → 最小验证方式（如用户需要排查）。若存在多个可能原因，按证据强弱排序，不要把猜测写成结论。

## 数据流架构图

第一部分（总）末尾必须给出一张紧凑的 ASCII 数据流图。禁止使用 Mermaid、PlantUML 或其他图形 DSL；节点标出模块角色，边标出传递的数据/状态/条件，至少包含输入、各核心模块和输出消费者。模块较多时可用分层或分支画法，不必强制单链：

```text
[输入/触发条件]
        |
        v
[入口文件:函数]
        | 调用参数/数据
        v
[模块A:函数] ---- 中间结果 ----> [模块B:函数]
        |                              |
        v                              v
[模块C:函数] <---- 汇总/通信 ---- [输出:直接消费者]
```

## 代码定位

图后必须给出“代码定位”，按执行顺序列出涉及代码的详细路径和实际行号：

在 Codex 回复中，工作区内的本地文件必须使用可点击的 Markdown 链接，链接目标使用绝对路径，并在目标末尾附上起始行号；不要只写反引号包裹的普通文件路径。例如：

```markdown
[common_cp.py](/home/x50063850/vllm-ascend-workspace/vllm-ascend/vllm_ascend/attention/context_parallel/common_cp.py:85)
```

```text
代码定位：
1. `[文件名](/绝对/工作区路径:起始行)` — `函数/类`：接收或产生什么数据。
2. `[文件名](/绝对/工作区路径:起始行)` — `函数/类`：执行什么关键处理。
3. `[文件名](/绝对/工作区路径:起始行)` — `函数/类`：输出由谁消费。
```

行号规则：

- 先用 `rg -n` 找符号，再用 `nl -ba <file>` 核对行号；不能凭记忆或猜测填写。
- 路径至少精确到工作区相对路径、文件名、函数/类和行范围；涉及多个仓库时注明仓库目录，例如 `vllm-ascend/...` 或 `vllm/...`。
- 行号应覆盖实际相关语句，而不是只标注整个文件；若源码未运行或行号可能因未提交改动变化，明确说明这是当前工作区的静态定位。
- 每个被讲解的模块至少有一个定位点；总数控制在 4-10 个，避免把无关调用全部列出。

## 分析流程

1. **确定入口**：从用户提到的 API、类、函数、日志关键词或配置项开始，用 `rg` 找定义和调用点。
2. **按源码顺序追踪**：沿着“触发条件 → 输入构造 → 核心判断/计算 → 返回或副作用 → 消费者”读取代码；跨进程、跨模块或跨 rank 时标明边界。
3. **划分模块**：把调用链切分为职责独立的模块（通常按文件/类划分），确定每个模块在数据流中的位置和交接的数据。
4. **提取证据**：记录关键变量在每个节点的形状、类型、值域、设备、rank/进程归属或异常条件，只保留解释所需的信息。
5. **组织输出**：先写整体数据流总述和架构图，再逐模块讲解设计，最后总结串回全局；静态分析、单元测试、真实服务/E2E 结果必须区分表述。

## 证据与措辞

- 已运行验证才写“实测/验证通过”；只读源码时写“从源码看/静态分析表明”。
- 没有足够证据时，明确写“可能原因”并说明还缺什么日志、环境或复现条件。
- 对分布式或异步流程，标明发送方、接收方、同步点和最终消费者，不能用单进程线性描述掩盖数据边界。
- 解释模块设计时用“它负责什么、为什么这么设计”的措辞，而不是逐行翻译代码。

## 最终格式

使用以下顺序，不增加额外的长篇章节：

1. 总述：整体数据流（1-2 段）+ ASCII 数据流架构图。
2. 分述：各模块设计（每模块一节，覆盖职责/输入/关键逻辑/输出交接）。
3. 总结：串回全局 + 设计关键点（错误类问题在此给出原因链）。
4. 代码定位：4-10 个带实际行号的路径。
5. 仅在必要时补充一行“验证范围/未验证项”。
